# Campaign update — Nov 15, 2026: Loom on gfx1100 — the toolchain is proven, the boundary isn't there

Zero GPU seconds, zero production contact, zero performance claims. The owner funded one
offline feasibility study — the "Loom" question: can AMD's codegen system remove a
producer-to-consumer memory trip or an exposed dispatch boundary in the routed-expert chain,
worth ≥1.020× committed decode tok/s? The predeclared contract allowed a CPU-only close as a
full answer, and the round delivered exactly that: **Loom is pinned and proven on gfx1100
CPU-side; the exposure arithmetic then closes the question — the hard optimistic bound
reaches only ~0.5× the serving bar, and the widest honest ceiling ~0.94×.** The most
reusable export is a byte-accounting rule the round had to learn the hard way: *prove the
intermediate's memory trip exists before pricing its removal* — the round's own table first
"cleared" the bar by pricing 30,720 B/entry of writes that never happen on this deployment.

## What Loom is, and what is now proven on gfx1100

[`hrx-loom` 0.1.0](https://pypi.org/project/hrx-loom/) (Apache-2.0 WITH LLVM-exception;
release commit `d01d1c18` of ROCm/hrx-system) ships the Loom compiler, runtime, model tools
and Python APIs. The round pinned it — wheel `hrx_loom-0.1.0-py3-none-manylinux_2_39_x86_64.whl`
(22,272,294 bytes, sha256 `4d3897b8…` verified against the release
[SHA256SUMS](https://github.com/ROCm/hrx-system/releases/download/v0.1.0/SHA256SUMS)) — and
AOT-compiled a minimal kernel for gfx1100 ahead of time. Fresh-eyes verification established:

- `loom-compile --format=amdgpu-hsaco --target=amdgpu:gfx1100` produces a valid code object
  (`Machine: AMD GPU`, gfx1100 flags), **byte-identical across reruns** (sha256 `f1d2ac75…`,
  9,176 bytes) and **independent of environment and output path** (reproduced under `env -i`).
- The compiler is **host-side only**: it links no HIP/HSA runtime — an AOT compile costs no
  GPU time and cannot perturb a running deployment. That makes the toolchain compatible with
  this ledger's whole discipline: compile offline, touch the device only in granted windows.
- NOT_RUN, distinct from PASS: **device-side code-object load** — loading the artifact at
  runtime, reusing engine buffers, submitting on the caller's stream. No effect size is
  claimed without that, and it is precisely what a granted window would test.

For anyone else on RDNA3: the pin is reproducible from the public wheel and checksums alone.

## The exposure arithmetic: every coherent model of the bytes misses the bar

The bar: the deployed 1.020× serving gate needs ≥1.961% of decode wall (≈0.230 ms of the
11.73 ms/committed token). The estimates below come from verified tables — the trace stages
recomputed against the saved phase table with zero mismatches, every source citation checked
in the pinned tree, and the selfcheck's gates hardened with a mutation self-test so detection
power is provable:

| estimate | value | as a fraction of the bar |
|---|---|---|
| routed-chain fusion, **hard optimistic bound** | 0.95–1.01% | 0.48–0.52× |
| + shared-expert twin, launch-slot ceiling | 1.78–1.84% | 0.91–0.94× |
| + shared-expert twin, byte-aware ceiling | 1.55–1.68% | 0.79–0.86× |
| **plausible schedule** | 0.26–0.61% routed / 0.52–1.21% Σ | ≤0.62× |

This is **close, not park** — the bound itself misses, so no schedule credibility can save
it — and **not blocked** — the verdict is invariant across every coherent model of the
disputed bytes. The window-1 arc's answer (no qualifying candidate for the 2% bar) now
extends to the codegen route.

## The phantom-writes trap: the table that "cleared" priced writes that never happen

The round's own byte table first showed the fused candidate at **2.19% — above the bar**.
The defect: it credited **30,720 B/entry of intermediate writes** (h floats to global memory
plus their reread). On this deployment those writes **do not exist**: the production
configuration runs the single-launch conversion path (`sw_v1=false`, `had_block=0` → one
conversion kernel per grouped call), so the swiglu h floats are produced and consumed with no
global round trip. Corrected constants: **5,840 B written / 5,840 B reread**. The corrected
bound kills the candidate.

The rule, banked with the measurement lessons: **a byte ledger that prices memory trips
which don't exist overstates the prize.** Before pricing any fusion: name the kernel that
writes the intermediate, the kernel that reads it, and the configuration flag that selects
between the production variants — then price only the trips the deployed configuration
actually takes. This is the accounting-side twin of the window-1 lesson that a lossless
repack which *adds* payload bytes loses on a bandwidth-bound dot: first the payload was wrong
(+22% bytes), now the trip itself was imaginary.

## The candidate kernel already exists in the tree

The best-priced boundary — fuse the swiglu+q8_1 conversion into the gate/up producer, emitting
the exact existing down-input representation — is implemented upstream behind
`STRATA_GU_SWIGLU` (`native_gu_swiglu_kernel` / `launch_gu_swiglu`): **default-on for CUDA,
off by default on HIP** (the env check precedes the HIP branch, so the flag would enable the
arm on gfx1100 without a rebuild). A donor result (RTX PRO 5000) records +0.5–0.9% decode,
bitwise-equal, 6/6 — feasibility evidence only, and consistent with this round's plausible
band (0.5–1.2%), not with the 1.961% bar. The knob stays off: enabling it would be a live
experiment on production with no priced case, and no window was requested.

## Reopening conditions

If this chain is ever reopened, the smallest discriminating counter is a **per-sub-stage
exposed-time stamp inside the grouped expert call** (gate/up vs swiglu+convert vs down, VRAM
share, both layer kinds) plus the regenerated and gated intermediate-bytes group (the
corrected constants above, gated so the phantom-writes class cannot recur). Together they
turn the launch-slot ceiling and the trip term into measurements. Any device-side Loom claim
additionally needs a granted window — the prior grant is consumed.

## Process notes and the NOT_RUN ledger

- The round ran as one orchestrated workflow: a local model worker did the bulk coding (pin,
  tables, gate fixes) under frontier-owned gates, and every worker deliverable was re-verified
  by an independent verifier that personally reran the decisive checks (byte-identical compile,
  selfcheck twice, sha-stability across the selfcheck, trace recomputation, source-citation
  sweep). Two frontier-authored selfcheck gate bugs were caught by the runner's own checks and
  fixed by a fresh packet under a hard invariant — no gate may be weakened, and an in-memory
  mutation self-test proves detection power survived.
- The failure taxonomy across passes is itself exportable: an unreachable model backend (the
  proxy answered while the engine behind it was down — probe the engine, not the proxy), a
  premature worker turn-end (fixed by a hard exit criterion: the turn ends only when the
  decisive check exits 0 or a named blocker is recorded), and the two gate bugs.
- NOT_RUN, distinct from PASS: device-side code-object load and any device execution of the
  compiler output; measured DRAM bytes for every byte row (logical bytes only — the L2
  discount is unpriced and only weakens the fusion's case further); the isolated per-sub-stage
  exposed time inside the grouped call; uninstrumented stage times; the isolated prototype,
  device replay and serving qualification — all moot at close.

## The close

No performance claim exits this round. What it changed: **Loom is proven on gfx1100
CPU-side** — reproducible from public artifacts, the first such datum on this ledger — the
codegen-route question is answered cheaply (no fused schedule reaches the bar, invariant
across byte models), a new measurement rule is banked (price only trips that exist), and the
in-tree `STRATA_GU_SWIGLU` arm is recorded with its donor context so nobody re-derives it.
The deployed stack is unchanged; the board stays fully dispositioned — zero promotions — with
both reopen doors named.
